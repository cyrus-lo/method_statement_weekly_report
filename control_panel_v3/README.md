# Workflow Control Panel V3

V3 is a separate localhost-only control panel. It defaults to `127.0.0.1:8767`, preview-only mode, and V3-owned data/workbook/browser roots. The application shell, period database, archive boundary, Step 0 CSV export, Step 1a review-workbook, first-date lookup, Step 1b finalization, Step 2 SMM summary, and independent weekly-report workers are implemented. First-date lookup is gated on a successful Step 1a run; Step 1b is gated on lookup success; Step 2 normally requires Step 1b success, with an explicit operator confirmation available only when no Step 1b run exists. Weekly reporting does not depend on any ECM workflow.

## Isolation requirements

- Do not modify V1 or V2 source files, tests, databases, run evidence, browser profiles, CSVs, templates, or workbooks.
- Writable V3 paths must be under `control_panel_v3/`, must not overlap each other, and must never point into V1/V2 paths.
- Shared immutable source templates may be read to seed V3-owned copies; do not edit those source templates in place.
- V2 history was imported once into a separate archive using a read-only source connection. Imported runs do not satisfy active V3 workflow gates.
- Open **V2 Archive** in the navigation to browse imported runs, their logs, and archived artifacts. The archive database is accessed read-only; repeat imports are refused unless the archive destination is empty.
- Keep all V3 tests in `control_panel_v3/tests/`.

## Setup and operations

Copy `.env.example` to `.env` only when local overrides are required. Run `start_control_panel_v3.ps1` to provision the V3 virtual environment and start the panel on the configured localhost port (8767 by default). Startup refuses port conflicts and waits for the V3 HTTP health check. The initial panel is preview-only. Use `restart_control_panel_v3.ps1` for a safe V3-only restart; it refuses active child processes unless `-Force` is explicitly supplied. See [OPERATIONS.md](OPERATIONS.md) for preflight, preview rehearsal, live cutover, restart recovery, and rollback steps.

## Current implementation boundary
For first-date lookup, the Step 0 CSV validates row identity while Excel column P supplies the normalized search value. The worker verifies ECM All versions and the OUT/Starts With criteria, rejects stale or unverifiable results, waits for pagination updates, and logs per-query result dates. See [OPERATIONS.md](OPERATIONS.md) for live-use safeguards.

The period lifecycle and isolated history database are implemented. Step 0 exports the approved saved search into a timestamped run-specific CSV plus an exact-period CSV handoff, validates the 11-column contract, and stages both publications before replacing either destination. Step 1a consumes only that exact-period handoff, applies readiness/version rules, backs up the active V3 review workbook, and atomically replaces the period sheet while preserving unrelated workbook content. The ECM and SMM templates are copied into V3 working storage; if absent, the separate V3 readiness workbook is seeded once from the V3 SMM template at `working/readiness/SMM_KMS_PM_Master_Document.xlsx`. Step 1a and Step 2 read this V3-owned input independently of the persistent SMM output; later readiness updates are not overwritten by startup. The outgoing-reference lookup validates each row against its exact Step 0 CSV identity but takes the search value from Excel column P (`Outgoing ref. no. (without revision)`). Before each `Search ECM Document` query, it selects and verifies `All versions`, `In/Out = OUT`, and `Outgoing ref. no. = Starts With`; it reads back the submitted Excel reference, waits for fresh results and pagination updates, logs returned dates, then saves the oldest returned date into column M. It supports `all`, `blank`, and `previously-unmatched` worker rerun scopes; the latter two preserve populated Remark cells. Successful runs write a JSON count/row summary, and the run detail page warns when there are unmatched rows. Rows with Count (Y/N) = N or a blank Document revision are skipped. Step 1b validates all applicable rows before changing anything, applies the strict cutoff (dates on or before 2026-04-16 are Count=N), stages a pre-run backup and a post-run snapshot, and commits only after the Excel Count=Y filter succeeds. Rows without a Document revision become Count=Y without requiring a first-date Remark. Step 2 validates all Count/SMM/KMS decisions and readiness mappings before mutation, writes static Display values into a staged ECM workbook, builds a year-aware period Summary from the configured V3 SMM template, and transactionally publishes the ECM update, SMM workbook, and post-save backup with rollback copies.

ECM browser workers use the dedicated V3 persistent Edge profile. Manual SSO/MFA recovery is supported; credentials are never automated. Page-scoped cursor pacing uses Playwright locators and a DOM-event fallback, never the desktop-wide cursor. Set `CONTROL_PANEL_V3_RESET_EDGE_PROFILE=true` only for an intentional profile reset; the old profile is renamed to a timestamped backup first. Browser failures may save a screenshot, DOM snapshot, and bounded diagnostics JSON under the failed run. Screenshots and DOM snapshots can contain sensitive ECM data: treat them as restricted operational evidence, retain only as long as local policy requires, and do not share them casually. Diagnostics JSON omits page text and strips URL query strings and fragments.

### Step 0 browser behavior

Step 0 defaults to opening the dedicated V3 Edge profile visibly from the start. If SSO/MFA is required, the operator completes it manually in that window; the run then continues on the same page. Credentials and MFA are never automated. Optional headless mode provides a visible sign-in fallback when needed and enabled. V3 must not use, copy, or reset the V2 profile. A fresh V3 profile can require sign-in; operator-approved live validation is still required.

The V3 configuration and builder consume these settings. Restart V3 safely to load configuration changes; mocked tests do not establish live ECM authentication:

| Planned setting | Planned default | Purpose |
| --- | --- | --- |
| `CONTROL_PANEL_V3_STEP0_HEADED` | `true` | Open Edge visibly from the start; `false` selects headless mode. |
| `CONTROL_PANEL_V3_STEP0_LOGIN_IF_NEEDED` | `true` | Allow manual sign-in when required, including visible fallback in headless mode. |
| `CONTROL_PANEL_V3_STEP0_TIMEOUT_SECONDS` | `60` | Step 0 browser operation timeout in seconds. |
| `CONTROL_PANEL_V3_STEP0_AUTH_TIMEOUT_SECONDS` | `120` | Manual authentication wait in seconds. |
| `CONTROL_PANEL_V3_STEP0_FAILURE_BROWSER_HOLD_SECONDS` | `120` | Bounded visible browser hold after failure, in seconds; `0` disables the hold. |

The operation and authentication timeouts must be positive, and the failure hold must be non-negative. The overall `CONTROL_PANEL_V3_JOB_TIMEOUT_SECONDS` must allow enough time for these waits and the work itself. Until the parity implementation is in place, the current builder uses `CONTROL_PANEL_V3_WORKER_TIMEOUT_SECONDS` and enables manual login; do not rely on the planned settings to alter a run. See [OPERATIONS.md](OPERATIONS.md) for the operator and verification boundary.

### Independent weekly report

The weekly Method Statement report is launched from its period row, independently of the ECM gates. Its sole PostgreSQL and reporting-timezone settings source is the workspace `django/.env`: set `PGHOST`, `PGDATABASE`, `PGUSER`, and `PGPASSWORD` for a read-only account. `PGPORT` defaults to `5432`, `PGSSLMODE` is optional, and `REPORTING_TIMEZONE` defaults to `Asia/Hong_Kong`. V3 reads this file only for a weekly run, validates its settings without loading them into the web process environment, and passes the required values only to the isolated worker environment; credentials are not put in command-line arguments or logs. Keep V3 paths and the weekly template in V3's own `.env` configuration. Install V3 dependencies from `requirements.txt` to add `psycopg[binary]`.

The weekly worker reads the existing report implementation and two SQL files from `django/` without modifying them. Provisioning makes a V3-owned copy of the workbook template in `working/templates/`; the worker reads that copy and writes an atomically published workbook into a run-specific directory under `working/django/`. The completed workbook is also copied into that run's artifact store for download. Each run uses inclusive selected-period dates. The source template, SQL, and implementation are read-only. The canonical `django/.env` is read for settings only; do not copy credentials into V3's `.env`.

The V2 run history and evidence archive has been imported under `control_panel_v3/archive/`; use the **V2 Archive** page for browsing. Archive runs and periods are display-only and remain completely separate from V3's active period dashboard and gates. The archive import refuses a non-empty destination.

Step 0, Step 1a, first-date lookup, Step 1b, Step 2, and weekly reporting have live command builders. Step 2 normally requires Step 1b success; its separately confirmed bypass is accepted only when no Step 1b run exists (queued, running, or failed Step 1b blocks it), and is persisted in run history. Weekly reporting has no ECM gates and writes a separate run-specific workbook. Workbook-mutating runs serialize access to V3 workbooks. Step 1b's Excel COM filter stage requires Windows with desktop Excel available. Step 2's source layout defaults to the V3 template sheet `(WIP) 1 Jul - 12 Jul`; the exact same-period collision is rejected before mutation. A same-period rerun replaces only that year-aware generated summary, and the period backup reflects the post-save workbook. The first-date lookup rerun scope and previous hit/miss counts are exposed in period history, and scope is recorded on the run. Step 1a handoff validates that its source is the latest successful Step 0 for that period. Run detail provides bounded status/log/artifact polling. No live ECM, database, or Excel workflow execution has been performed; passing tests and the health check are not live integration certification. V3 defaults to preview-only; switching to live mode is an explicit local action.

The first-date lookup validates row identity against Step 0, submits the normalized value from Excel column P, selects and verifies ECM All versions and the OUT/Starts With criteria, and refuses stale or unverifiable results. Per-query result dates and pagination are logged; see [OPERATIONS.md](OPERATIONS.md) for the operator checks.
